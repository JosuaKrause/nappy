# minty-quail — test_main.gd drives public seams and real frames · 2026-11-01


minty-quail's `tests-public-seams.md`, slice 4: `tests/test_main.gd`. The player allows the item in slices
alongside the other steps "as long as the final result is the same" (inbox #813 in curly-moose); the item is done
suite by suite. The item's rule for a seam is that the game itself can use it: a public member only a test reads is
not a seam, however it is named.

**Counts, before -> after.** Private reads are what `rg -v '^\s*#' <file> | rg -o '\._[a-z]\w*'` finds; direct frame
calls are `rg -v '^\s*#' <file> | rg -c '\._(physics_)?process\('`.

| `test_main.gd` | 386 -> 3 | 18 -> 3 |

The three left are the same three lines, in one block: the readout's text is rebuilt on an interval counted in the
frames' own `delta`, and one test steps `DebugReadout._process(delta)` with an injected delta (with the readout's own
processing switched off) because a real frame's length is not the 16 ms the check means. The first step is a full
interval, which rebuilds the text and starts the interval over at exactly `READOUT_INTERVAL`, so the 16 ms step always
lands inside it and the last step always lands past its end; without it the real frames already awaited have counted
the interval down by an unknown amount and the check fails on a slow frame. It says so where it stands.

**Built.**
- `main` is booted for real wherever a check is about what it builds or connects. `scenes/main.tscn` is configured
  through `main.configure()` (public), two frames let its `_ready()` finish, and the rest is what a player or the
  engine does: a real touch on the title's own button, the screens' output signals, the engine's focus notification on
  the `ReturnWindow` node, real physics frames, and a real stall of a frame (`OS.delay_msec`) for the lag spike. Nodes
  are found by the names and classes the scene gives them; nothing is read off `main`.
- Four seams were added, each used by the game or by its own owner:
  - `Main.use_reload(reload: Callable)` and `Main.use_quit(quit: Callable)`: what `main` calls instead of reloading the
    scene or quitting the tree. A boot never handed one reloads and quits as before. `use_reload()` is the one writer of
    the field behind it: `test_run_flow.gd`, `test_run_checkpoints.gd` and `test_save.gd` call it too.
  - `ReturnWindow.use_clock(clock: Callable)`: the milliseconds the half second is measured on, the wall clock for a
    window never handed one (the pattern of `ModeButton.use_clock()`). The suite steps across the window's end by moving
    a clock, where it wrote `_ignored_until_msec` before.
  - `ControlsMode.forget()`: the pair of `remember()`, the process-wide title answer put back to "none", where the
    suite wrote the three statics. The game does not call it; the test runner's reset between suites does, beside
    its own `GameSave` and `TitleScreen` resets, until hidden-statics moves this state to an owner.
  - `SceneRecipeRuntime.settle_camera_on(camera, player)` is public and static; `_settle_starting_camera()` calls it
    with the viewport's camera and its player. The suite settles a camera on a stroller with it.
- `DebugReadout`'s `setup()`, `watch()`, `open_the_title()`, `close_the_title()`, `show_for_the_walk()`,
  `graph_on()` and `readout_on()` were already public and are all the suite needs; the graph and the note are found by
  the names the readout gives them (`FrameGraph`, `DebugModeNote`), and the keys are pushed through the viewport.
- The ground checks read the city's `Ground` node (`SceneryGround`) by its name; `has_water()`, `keys_in()` and
  `get_cell_source_id()` are its public methods.
- The flags checks read the run's configuration (`RunConfig.parse()`), which is where `main` reads `no_focus_pause` and
  `is_rig` from, where the suite called `DevFlags`' private parsers.
- `main.gd`'s comments no longer name `tests/test_main.gd` as the driver of a script-only `main`; the guards they
  explain stay, since other suites still drive one.

**Rejected.**
- A public `main` accessor for the flow, the day or the summary: the game reads none of them from outside. The flow's
  step is read where the game shows it (a continue that reloads, a screen that is up), the day through its node.
- A test-only method on `DebugReadout` to advance the interval; the one direct `_process(delta)` is the allowed
  exception, with the readout's own processing off.
- Re-opening the title on one booted game to press a second button: the title opens once, at boot, so each answer is
  its own boot.

**Parity: old check -> new check.** Every test function keeps its name except where this table says; the checks that start from one title share a boot, so the walk, the focus and the ending are `_check_` steps of `_test_a_session_on_one_booted_game`. The two
rig-flag tests, `_test_is_rig_from_args` and `_test_rig_quit_seconds_from`, were never called from `run()`: they run
now, and the one expectation that was false (a 5 s day reading as the margin alone; it reads 5 s plus the margin) is
the day-length-0 case beside it.

**Cost.** The suite boots the real game four times where it built a city by hand six times: the left-joystick boot
(with the rig flags), the right-joystick boot, the escape's boot and the session boot. Measured alone on one machine,
the first version of this slice (nine boots) took 41.8 s while it was loaded; the four-boot suite takes about 22 s
unloaded (21.4 to 22.4 s over three runs) against 2.4 s for the suite that built a city by hand. A boot costs 2 to 5
s, most of it `main` generating and starting the first day. The four cannot be shared further: a title opens once per
boot and each of the left press, the right press and the key start is a different answer to it; the escape's boot is
the only one that begins in a section with its brief up, and it needs the right answer left remembered by the boot
before it. `tests/suite_costs.txt` is written by a runner and not by hand, so the shard planner's number for this
suite is the next cost-table refresh's.
