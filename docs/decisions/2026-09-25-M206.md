# M206 — The screen after a game over or a held restart is the right way up · built 2026-10-04

*([PLAYTEST-140](../playtests/PLAYTEST-140.md), statement 5: "also there is a bug when you lose
with game over the title screen is sideways", on the phone; [PLAYTEST-144](../playtests/PLAYTEST-144.md),
statement 26, the still captioned "This is the screen when resetting". Asked on 2026-10-04 whether
they had checked it again on the phone, the player: "hmm, I gave you all the info on that already.
what else do you need?" (inbox #514), so it was reproduced from the recorded evidence.)*

**Built (PR #523).** Both reports are one bug. A game over's continue and a held restart from a
day summary both reload the scene (`main._restart_run()`). The root window survives the reload with
its portrait box, but the new boot's first frames are drawn by a boot camera that was never turned,
because `_apply_orientation()` waited for the mother, the HUD and the touch controls. So the city
at the doorstep showed upright, filling the portrait screen, for the rest of the boot before the
turned title appeared. A first page load does not show it, because the page's splash covers the
canvas until the boot finishes.

`_apply_orientation()` now turns the window's box, the boot camera and every screen layer already
built before anything else exists; the part that needs the mother, the HUD and the touch controls
still waits for them. The camera's rotation has one definition, `ScreenOrientation.apply_to_camera()`,
which the boot camera and the mother's camera both use (M60's "one rotation, applied once").
`tests/test_camera_start.gd` boots into a portrait touch window and checks the box and the boot
camera at the first frame; it fails on the code before the fix.

**Measured** in desktop Chrome emulating a portrait touch phone (412x915), on the released page
(v0.23.0), a local release export before the fix and one with it: before, the upright frames lasted
1.81 s after a held restart and 1.97 s after a game over on the released page, and 1.80 s and 1.88 s
on the export before the fix; with the fix, the same
frames are turned like the title. One run of each; method, strips and timings in
`docs/evidence/m206-title-upright-2026-10-04/`. No phone run; the review item asks for one after
the release.

**What PR #378 settled first, and still holds.** The orientation is asked again as the title opens,
and two suspects are ruled out on the web export: touch detection is the browser's fixed
`'ontouchstart' in window`, and the window size is re-read from the canvas every frame, so the
per-frame orientation poll (`main._process()`, which runs through pauses) cannot stay wrong for
more than a frame once the game is running. What it did not reach is the boot's first frames after a
reload, which come before that poll and before the mother exists.

**Proposed, not asked for, and open to overturn:** the warm-up frames are turned rather than
covered, so the city shows turned and undimmed for about two seconds before the title; every screen
layer already built is turned during the warm-up, not only the camera and the box;
`Stroller.set_screen_rotation()` takes a bool and delegates to the shared rotation.

**Left as it is:** the `DEBUG MODE ON` label, which exists only under `?debug=1`, is drawn unturned.
**Seen, not investigated:** in the headless browser, taking a screenshot while the GAME OVER screen
showed restarted the run both times; it may be the capture itself or a restart on a focus change.
