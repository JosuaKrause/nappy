# M159 — On the web the frame can go straight to the screen, and the page can draw fewer pixels · 2026-10-12

[velvet-marten](../playtests/2026-10-11-velvet-marten.md), #700: "I wouldn't go to hack the engine
just yet. We can try the direct to screen first (if it's an in engine setting), then the internal
multiplier".

**Built, both behind the debug gate** (a debug build, or a release page with `?debug=1`, as
`?controls=` is), so the player can compare on the phone:

- **`?direct=1`** calls `RenderingServer.viewport_set_render_direct_to_screen()` on the root viewport,
  web only (`WebDisplay.apply()`, `src/web_display.gd`, from `Main._ready`). It is not on by default:
  in a desktop Chrome web debug export the page is solid black with it on, the game running and the
  console clean, also with the call deferred a frame; the cause is not found. Nothing can read the
  root viewport's texture while it is on: `Telemetry`'s snapshot and burst on the web
  (`?telemetry=1`) and `AutoScreenshot` read nothing. Native builds are unchanged. Orientation and
  letterbox with it on were not checked, since the page is black.
- **`?dpr=<x>`** caps `window.devicePixelRatio` at the smaller of the browser's ratio and `x` (below
  0.25 or not a number is ignored) and resizes so the engine redraws; there is no default cap, the
  value being the player's after two phone records. The frame record and the readout read that ratio
  and the canvas, so they show the capped values ([M159-9](2026-09-19-M159-9.md)). In desktop Chrome
  (ratio 2, window 1230×811) `?dpr=0.5` draws 615×405, `0.75` 922×608 and `1` 1230×811
  ([web-dpr-cap-2026-10-12](../evidence/web-dpr-cap-2026-10-12/)).

*Open to overturn, chosen by the implementer:* `?direct` and `?dpr` are not in
`DevFlags._LIVE_DEBUG_QUERY_KEYS`, since they change nothing in play.

**Verified** by `tests/test_web_display.gd` and the desktop-browser canvas sizes above; nothing on a
phone. Not built, as the player said: patching the engine's web template.
