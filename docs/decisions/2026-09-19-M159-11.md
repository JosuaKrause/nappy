# M159 — On the web the page can draw fewer pixels; the frame cannot go straight to the screen · 2026-10-12

[velvet-marten](../playtests/2026-10-11-velvet-marten.md), #700: "I wouldn't go to hack the engine
just yet. We can try the direct to screen first (if it's an in engine setting), then the internal
multiplier".

**Direct to screen cannot work on the web build, and is not built.** It is an engine setting,
`RenderingServer.viewport_set_render_direct_to_screen()` on the root viewport. Tried behind a page
parameter, it drew a solid black page in a desktop Chrome web debug export, the game running and the
console clean. The review read the cause in the Godot 4.7 source (not proved with a patched build):
in the Compatibility renderer the frame's only buffer swap happens inside the root viewport's copy to
the screen, and that copy is what direct to screen skips; on the web, whose context draws into an
offscreen buffer (`explicitSwapControl`), that swap is `emscripten_webgl_commit_frame()`, the call
that puts a frame on the visible canvas. So the game renders every frame and shows none, on every
browser. The parameter was removed rather than kept, since it can only ever show a black page.
*Untested, for the player:* a tiny second viewport attached to the screen, whose own copy would make
the swap, at the cost of one overwritten pixel and perhaps a frame of delay. Patching the engine's
template is what the player ruled out for now.

**Built: `?dpr=<x>`**, behind the debug gate (a debug build, or a release page with `?debug=1`, as
`?controls=` is), caps `window.devicePixelRatio` at the smaller of the browser's ratio and `x` (below
0.25 or not a number is ignored) in `WebDisplay.apply()` (`src/web_display.gd`, from `Main._ready`).
The engine re-reads the ratio on its per-frame canvas-size check, so the cap holds through rotation
and fullscreen, and touch positions scale with the canvas. There is no default cap; the value is the
player's after phone frame records. The frame record and the readout read that ratio and the canvas,
so they show the capped values ([M159-9](2026-09-19-M159-9.md)). In desktop Chrome (ratio 2, window
1230×811) `?dpr=0.5` draws 615×405, `0.75` 922×608 and `1` 1230×811
([web-dpr-cap-2026-10-12](../evidence/web-dpr-cap-2026-10-12/)). README, `docs/ARCHITECTURE.md`
and `DevFlags.readout_requested()` list it among the gated parameters.

*Open to overturn, chosen by the implementer:* `?dpr` is not in `DevFlags._LIVE_DEBUG_QUERY_KEYS`,
since it changes nothing in play.

**Verified** by `tests/test_web_display.gd` and the desktop-browser canvas sizes above; nothing on a
phone.
