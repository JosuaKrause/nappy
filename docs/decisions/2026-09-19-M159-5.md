# M159 — Every frame's time by system, slow frames marked · 2026-10-04

*([quiet-yak](../playtests/2026-10-03-quiet-yak.md), #510: "let's focus on recording what cause
spillover in the regular 2ms and we can probably investigate further here. it seems that stuttering
happens with a lot of objects on screen so influence calculation, pathing, drawing, etc. can all be
the culprit"; asked, "Every frame, slow ones marked" and "Download plus readout line"; then "my
hypothesis is that mode 2 allows more expensive things to take up time as it limits itself to a very
short time budget.")* Built in PR #521.

**What is built.** `--frame-record`, or `?debug=1&framerecord=1` on the released page, keeps every
play frame's time for the last five minutes or so (a ring of 18,000 rows), split into nine buckets
that add up to the frame exactly: `scenery`, `crowd`, `influence`, `events`, `cues`, `draw`,
`physics_rest`, `process_rest` and `wait`. `scenery` includes a deferred window around everything
the residency update queues for the engine's flush (a region's tile-map update, a newly resident
building's, shadow's or decal's first draw), in every ground mode, so mode 1 and 2's deferred work
is not charged to `draw`; its share is also `scenery_deferred_usec`. Each row also carries how far
the queue ran past its 2ms, its jobs by kind with guard preparations apart, and the world counters.
A slow frame is one longer than 1.5 display budgets; one whose callbacks fit a single budget counts
as `outside_callbacks`. The page has a `save frames` button that downloads the record as JSON, and
the readout a line naming the last slow frame's largest costs. The file carries the clock's
measured step (`timer_resolution_usec`, since a page's clock is reduced-precision), the cost of one
timing pair, a note per bucket, a note that there is no GPU time, and a summary split by slow frames
with and without a scenery job, which is the split that answers the hypothesis.
[TELEMETRY.md](../TELEMETRY.md) carries the format under "Per-system frame records".

**Measured** (Apple M2, windowed, seed 67 along the player's route, five rotated rounds; evidence
in [m159-frame-record-2026-10-04](../evidence/m159-frame-record-2026-10-04/README.md)). The first
wraps cost every player 0.16ms of mean frame with the record off, so a crowd agent and a live event
copy the switch when made and pay one member read; after that, off and `main` sit within run-to-run
noise. On, the record costs 0.25 to 0.63ms of mean frame. On the desktop, past each day's load,
mode 1 had 49 slow frames and mode 2 had 18. Nearly all carried a near-constant 19.3ms in `draw`,
with `scenery` about 0.25ms on average and draw calls only modestly up. On a native window the
buffer swap's wait is charged to `draw`, so these are most likely presentation stalls rather than
drawing work, and an optimization should not read them as drawing. The desktop does not show the
player's hypothesis; the phone's file is what can.

**Accepted by the player** (inbox #526, 2026-10-04, "Accept all three"): the timing wrap in
gameplay classes, written into the **telemetry** skill as its one exception to "Per-frame checks go
in the observer"; the download as the one file-writing word on a released page, recorded as an
overturn in [M193](2026-09-25-M193-the-live-pages-debug-1-reaches-the-debug-flags.md); and "slow"
as longer than 1.5 display budgets.

**Open to overturn** (the builder's choices where the item was silent): the page records only
with `&framerecord=1` on top of `?debug=1`, so an ordinary debug page pays nothing (the option read
"under ?debug=1 a button saves"); the readout names fewer than three costs when three do not fit
its width (the option read "top three costs"); the button is a page element at the top centre,
labelled `save frames`, not a game control, since a touch on the canvas also steers her; crowd
agents are timed one by one, since they share the y-sorted layer with events and props; a crowd
agent or live event copies the switch when it is made, the once-a-frame systems read it each frame;
a page assumes 60Hz, since a
browser reports no refresh rate (`refresh_assumed: true`); the most recent frames are kept, not the
first; only play frames are kept, including a day's loading frames; the record survives a held
restart; the escape builds no recorder, and leaving the day switches the timing off and hides the
button; the deferred scenery work is caught by a window around the flush, not by flushing inside the
budget as mode 3 does, since flushing inside would change how many regions mode 1 prepares a frame.
