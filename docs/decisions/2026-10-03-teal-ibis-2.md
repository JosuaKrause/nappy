# teal-ibis — Measured disk preflights and browser scratch removed by ownership · built 2026-10-03

*([snowy-newt](../playtests/2026-10-03-snowy-newt.md): measure what accumulates and add safeguards
so the drive does not fill, and have finished jobs clean up their temporary data; the first half is
[teal-ibis](2026-10-03-teal-ibis.md))*

**Built (PR #476).** Two halves.

**A batch the volume cannot hold is refused before it starts.** `tools/measure-disk-peak.sh` runs
a command while sampling `du` of the paths it writes and `df` of their volume, and reports the peak
additional allocation. Measured on 2026-10-03 (method, environment and results in
`docs/evidence/teal-ibis-headroom-2026-10-03/`): a sparse worktree 24 MiB, a full worktree
1.08 GiB, an atlas bake 1.1 MiB, an import 1 MiB, a debug and a release Web export 39 and 33 MiB, a
Web-template build on a cache miss 2.70 GiB (7 MiB kept), a headless scene recipe about 11 KiB, one
with its still 436 KiB, and a recording about 9.5 MiB per recorded second. `tools/lib_disk_headroom.sh`
holds one estimate per job, the measured peak plus a stated margin, and a tool refuses when the
destination volume's free space is below its batch's estimate, naming what is free, what is needed
and from which parts, the shortfall, a smaller batch where there is one, and the cleanup step; below
the estimate plus a 3 GiB reserve it warns with the same figures and runs. The player chose the
warning over a refusal (inbox #496: "Yes tool should warm and only refuse if it's not possible"),
and the using-tools and orchestrating skills say a warning stops new tasks until the space is
sorted out. An unmeasured job, an unreadable `df` or a malformed setting refuses rather than
guessing. It runs after argument validation, so `--help` and a rejected argument never reach it, in
`build-web-template.sh` (cache miss), `export-web.sh`, `bake-atlases.sh` (when it bakes),
`scene-recipes.sh` (per recipe), `shot.sh`, `record.sh` (per game second it may record) and the import
repair of `run.sh`, `shot.sh` and `record.sh`. `tools/test_disk_headroom.py` tests it against a stub
`df` and a stub Godot, never a real drive. `tools/trailer.sh` is still open in the entry.

**Browser scratch is removed only when the run that made it is proven to own it.** Headless Chrome
on macOS copies its own bundle on every launch, about 2.1 GiB allocated, and removes the copy only
on a graceful close; `browser-check.mjs` used SIGKILL, which left one behind per run. It now
launches Chrome with `--disable-features=MacAppCodeSignClone`, which stops the copy being made,
closes it through CDP and waits for it to exit (SIGTERM, then SIGKILL, only as fallbacks), and
writes `scratch.json`. `browser-scratch.mjs` removes a copy only when `lsof` showed this run's own
browser holding a file inside it and, after every process of the run has exited, nothing on the
system holds it; any other copy that appeared during the run is reported as a candidate with the
missing evidence named, and left alone. `browser-scratch.test.mjs` runs against fixture directories
only.

**The player's choice:** the 3 GiB reserve (the player's warnings started at about 2.5 GiB free)
is the same for every job and only warns, so no job is refused for want of it. **Proposed, not
asked for, and open to overturn:** estimates above the measured peaks by +27% (full worktree), +34% (sparse worktree),
+48% (template build) and +65% (Web export), while the small jobs are rounded up to a few MiB,
several times their measurement (import 16 MiB against 2.1 MiB, atlas bake 4 against 1.1, still
4 against 0.4, recipe with still 2 against 0.4, headless recipe 1 MiB against about 11 KiB);
512 KiB a frame for recordings, about 3.3 times the 160 KiB quiet frames measured and 25% over the
410 KiB busy still, so 31 MiB per recorded game second: a full route day is refused below about
6.8 GiB free and warned below about 9.8 GiB; the `NAPPY_HEADROOM_CHECK=off` switch, which
says so every time it skips; and `tools/measure-disk-peak.sh` itself. Editing
`build-web-template.sh` changes the template's cache key, so the first release after this merges
recompiles the template.

**Verified.** `tools/check.sh`, `tools/lint.sh`, `tools/pycheck.sh`, `tools/test_cli_help.sh`; on
the real disk a one-recipe run passes the check and, with a huge reserve, refuses and writes
nothing; a full browser check against a release export closed Chrome through CDP, made no copy and
removed its profile.
